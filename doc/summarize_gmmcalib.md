# GMMCalib LiDAR Calibration Pipeline Explained

**GMMCalib** is a framework for extrinsic calibration of multi-LiDAR systems using a **Gaussian Mixture Model (GMM) joint registration** approach ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=object%20detection%2C%20but%20errors%20propagate,spatial%20transformation%20between%20sensor%20frames)) ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=However%2C%20among%20local%20registration%20methods%2C,methods%20aim%20to%20avoid%20selecting)). Instead of aligning scans pairwise (as in ICP), GMMCalib aligns all point clouds together in a common **latent calibration frame** by modeling the points probabilistically. This yields both a reconstructed target shape and the **extrinsic transform** (rotation and translation) between the LiDAR sensors ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=For%20LiDAR%20sensor%20setups%2C%20this,requires%20that%20one%20of%20the)) ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=The%20goal%20of%20extrinsic%20calibration,sensor%20frames%20are%20transformed%20into)). Below, we break down the process step-by-step, and walk through the `gmmcalib.py` code with detailed explanations of the major variables (`pcds`, `Xin`, `V`, `X`, `TV`, `AllT`, `T_1`, `T_2`, `T_calib`, `T_final`, etc.). We also clarify how the transforms `T_1`, `T_2`, and `T_calib` are defined in the code and how they relate to the extrinsic calibration error and sensor frame transformations.

 ([GitHub - TUMFTM/GMMCalib: LiDAR-to-LiDAR Calibration](https://github.com/TUMFTM/GMMCalib)) *Figure: Conceptual overview of GMMCalib’s pipeline. Multiple LiDAR point clouds (blue for sensor 1, green for sensor 2, etc.) are jointly registered in a **latent target frame** (black cube). The algorithm outputs a **calibration matrix** (extrinsic transform between sensors) and a reconstructed **target shape** (black points). The target shape can be compared to a known CAD model (blue) for validation.* 

## 1. Data Preparation and Input Processing

**Collect and prepare point cloud data:** The calibration procedure starts with collecting several frames of point clouds from each LiDAR sensor, observing a common scene (often containing a calibration target). All sensors and the target remain static during capture so that each frame pair is comparable ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=combines%20both%20simulation,world%20environment)). The more frames provided, the more robust the calibration. These point clouds (usually in `.pcd` format) are organized per sensor (e.g. `data/sensor_1/1.pcd`, `data/sensor_2/1.pcd`, etc.). GMMCalib’s configuration (`config.yaml`) specifies how to initially align these scans and define a region of interest:
- **Initial Transformations:** Optional approximate extrinsic for each sensor (roll, pitch, yaw, and translation). If known, this positions the point clouds in a common reference frame (e.g. vehicle or world frame) to aid calibration ([GitHub - TUMFTM/GMMCalib: LiDAR-to-LiDAR Calibration](https://github.com/TUMFTM/GMMCalib#:~:text=The%20config%20file%20currently%20has,four%20entries)). For example, `transform_sensor_1` and `transform_sensor_2` in the config might be arrays like `[roll, pitch, yaw, x, y, z]`.
- **Target Region (ROI):** If a calibration target is used and its rough location is known, `min_bound` and `max_bound` define a 3D axis-aligned bounding box to crop the point clouds around the target ([GitHub - TUMFTM/GMMCalib: LiDAR-to-LiDAR Calibration](https://github.com/TUMFTM/GMMCalib#:~:text=translation%20vector,range%20of%20the%20point%20cloud)). Otherwise, a broad range (e.g. `[-50,-50,-50]` to `[50,50,50]`) can be set.

**Reading and transforming point clouds:** The script uses `generatePCDs.generate_data()` to load and preprocess the PCD files ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=calibrate,T_2)). This function reads the config and applies the initial transforms and cropping:
- It loads the YAML config and extracts `transform_sensor_1`, `transform_sensor_2`, `min_bound`, `max_bound`, etc. ([GMMCalib/src/generatePCDs.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/generatePCDs.py#:~:text=config_data%20%3D%20yaml)).
- It then iterates over sensors and frame indices to read each PCD using Open3D. For each point cloud, it computes a homogeneous transform matrix `T_g` from the given roll-pitch-yaw and translation (using `transformPCDs.compute_global_transform`) ([GMMCalib/src/generatePCDs.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/generatePCDs.py#:~:text=pcd%20%3D%20o3d,pcd)) ([GMMCalib/src/transformPCDs.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/transformPCDs.py#:~:text=rotation_matrix%20%3D%20R)). This `T_g` represents the sensor’s pose in the *global/vehicle frame*. The code applies `pcd.transform(T_g)` to bring the sensor’s points into this common frame ([GMMCalib/src/generatePCDs.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/generatePCDs.py#:~:text=T_g%20%3D%20compute_global_transform%28transform_sensor_1)). In other words, after this step sensor 1 and sensor 2 clouds are roughly aligned in a global coordinate system (if the initial guess was accurate).
- It then crops the point cloud to the specified ROI around the target (using an axis-aligned box) ([GMMCalib/src/generatePCDs.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/generatePCDs.py#:~:text=)), removing points outside the target area (e.g., far-away clutter).
- All processed point clouds are appended to `pcds` list and returned.

In the main calibration function, these loaded clouds are stored in `pcds` (a list of Open3D point cloud objects) ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=calibrate,nObs)). The code then converts each point cloud to a NumPy array of point coordinates: `V = [np.array(cloud.points) for cloud in pcds]` ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=generatePCDs,X)). Here **`V`** is a list of point sets, with length `nObs` equal to the total number of point clouds from all sensors. If two sensors are used with N frames each, then `nObs = 2N`. By convention in this script, the first N point sets in `V` correspond to sensor 1’s frames and the next N correspond to sensor 2’s frames.

**Initial target shape guess (`Xin`):** GMMCalib optionally uses a calibration target (like a cube) to improve registration. Before alignment, the code creates an **initial model point cloud** `Xin` representing this target shape ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=generatePCDs,nObs)). The `create_gt.create_init_pc(box_size=(0.5,0.5,0.5), num_points=400)` call generates ~400 points uniformly sampled on the surfaces of a 0.5 m cube ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=generatePCDs,nObs)) ([GMMCalib/src/create_gt.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/create_gt.py#:~:text=)) ([GMMCalib/src/create_gt.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/create_gt.py#:~:text=points_on_face%20%3D%20vertices,vertices%5B0)). This cube is then shifted by `[9.8, 4.75, 0.38]` (an example offset) to roughly position it where the target is expected in the global frame ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=generatePCDs,nObs)). The result is **`Xin`**, an initial guess for the GMM centroid positions (the “latent” target frame points). If no specific target is known, `Xin` could be a coarse shape covering the ROI.

**Summary:** At the end of data preparation, we have:
- **`pcds`:** a list of cropped point clouds for each sensor frame.
- **`V`:** a list of NumPy arrays (each shape ≈ [M_i, 3]) of points from each point cloud.
- **`Xin`:** an initial set of model points (shape [K,3], e.g. K=400) representing the calibration target’s approximate shape/position.

## 2. Joint Point Cloud Alignment with GMM (Expectation-Maximization)

**Performing joint registration:** GMMCalib aligns all the point clouds in `V` simultaneously to the model `X` (initialized from `Xin`). This is done by calling `modelgenerator.jgmm(V=V, Xin=Xin, maxNumIter=100)` ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=np.array%28,V%3DV%2C%20Xin%3DXin%2C%20maxNumIter%3D100%29%20T_1)). The `jgmm` function implements a **joint GMM registration** algorithm (inspired by the method from Evangelidis et al. 2018 ([GMMCalib/src/modelgenerator.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/modelgenerator.py#:~:text=%E2%80%9CJoint%20Alignment%20of%20Multiple%20Point,Maximization%2C%E2%80%9D))) that uses an Expectation-Maximization (EM) approach to align multiple point sets and estimate a common shape:
- **Initialization:** The algorithm starts by transposing the data (for convenience) and setting the initial model `X = Xin^T` (K centroids in 3D) ([GMMCalib/src/modelgenerator.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/modelgenerator.py#:~:text=V%20%3D%20,in%20V)). It also initializes a rotation `R_i = I` (3×3 identity) and translation `t_i = [0,0,0]` for each point set *i* ([GMMCalib/src/modelgenerator.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/modelgenerator.py#:~:text=)) ([GMMCalib/src/modelgenerator.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/modelgenerator.py#:~:text=t%20%3D%20)). These serve as the initial guess for how each point cloud should be transformed to align with the model. Initially, since we already applied the coarse global transform, the clouds are roughly aligned, so identity/zero is a fine start for the residual alignment. The point sets are initially “transformed views” `TV[i] = R_i * V_i + t_i` (which is just V_i itself at the start) ([GMMCalib/src/modelgenerator.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/modelgenerator.py#:~:text=t.append%28np.array%28)).
- **E-step (Expectation):** In each EM iteration, the algorithm treats the model points `X` as centers of Gaussian distributions and each observed point in each `V_i` as a sample. It computes the probability (responsibility) of each model point explaining each observed point. Intuitively, this assigns each measurement point a soft correspondence to nearby model centroids. This step involves computing distance-based weights for each point relative to each centroid (using the current transforms R, t to bring points into the model frame) ([GMMCalib/src/modelgenerator.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/modelgenerator.py#:~:text=maxXYZ%20%3D%20np)) ([GMMCalib/src/modelgenerator.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/modelgenerator.py#:~:text=gamma%20%3D%200)). The algorithm also updates mixture weights `pk` for each centroid (representing the proportion of points associated with each model point) ([GMMCalib/src/modelgenerator.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/modelgenerator.py#:~:text=Transformations%20at%20each%20iteration)) ([GMMCalib/src/modelgenerator.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/modelgenerator.py#:~:text=pk%20%3D%201%2F%28K)).
- **M-step (Maximization):** Given those correspondences, the algorithm updates the model and transformations to maximize the likelihood. It adjusts the centroid positions `X` to better fit the aggregate of all point clouds (moving the “model” closer to the data) and optimizes each sensor’s rotation `R_i` and translation `t_i` to better align its points to the new model. This simultaneous update ensures all point clouds converge onto a single shape rather than one being fixed as reference. The rotations and translations are updated in a way that minimizes the error between transformed points and the model (often using closed-form solutions or iterative refinement for R) ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=,and%20as%20the%20reference%20frame)) ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=into%20the%20vehicle%20frame%20as,and%20as%20the%20reference%20frame)). After updating, the transformed views `TV[i]` are recomputed with the new R_i, t_i.
- **Iteration:** The E-step and M-step repeat, iteratively refining correspondences and alignment. Over ~100 iterations (as set by `maxNumIter=100`), the model `X` and transforms `R_i, t_i` converge.

**Outputs of GMM alignment:** The `jgmm` function returns four values: **`X`**, **`TV`**, **`T`**, **`pk`** ([GMMCalib/src/modelgenerator.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/modelgenerator.py#:~:text=X%3A%20array%2C%20shape%20)) ([GMMCalib/src/modelgenerator.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/modelgenerator.py#:~:text=Transformations%20at%20each%20iteration)):
- **`X`:** The final model point cloud (as a NumPy array of shape (N,3)) representing the reconstructed target or common structure. This is essentially the **latent target shape** after alignment. In context, `X` corresponds to points in the **calibration frame** coordinate system (the frame in which all scans now align). If a known target was used, `X` should approximate its shape (e.g., a cube’s point cloud).
- **`TV`:** A list of transformed point sets, where each `TV[i]` = R_i * V_i + t_i is the *i*th input point cloud transformed into the common frame (aligned with X). At convergence, these `TV[i]` should all overlap each other and with `X` as much as possible, indicating a good registration.
- **`T`:** A list of transformations per iteration. Specifically, `T[j] = (R_list, t_list)` for iteration j, where `R_list` is the list of all sensor rotation matrices at that iteration and `t_list` the list of translation vectors. The last element `T[-1]` contains the **final transforms** for all observations.
- **`pk`:** An array of length K giving the final mixture weights (probability of each model point). This can indicate which parts of the model were strongly supported by data (not critical for the calibration output, but useful for analyzing the target reconstruction).

In our code, the returned tuple is unpacked as `X, TV, AllT, pk = jgmm(...)` ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=np.array%28,V%3DV%2C%20Xin%3DXin%2C%20maxNumIter%3D100%29%20T_1)). Here **`AllT`** corresponds to `T` described above. We are mainly interested in `AllT[-1]`, the final iteration’s transforms.

**Key insight:** Unlike ICP, which yields a direct transform between two scans, this GMM joint registration aligns **both sensors’ clouds into an arbitrary common frame (C)** ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=clouds,and%20as%20the%20reference%20frame)) ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=into%20the%20vehicle%20frame%20as,and%20as%20the%20reference%20frame)). This frame is essentially defined by the estimated target/model `X`. Neither sensor is treated as a fixed reference; instead, both are adjusted (which helps avoid bias from picking a bad reference ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=registration%20methods%20such%20as%20Iterative,We%20perform%20simulation%20experiments%20using)) ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=match%20at%20L76%20However%2C%20among,methods%20aim%20to%20avoid%20selecting))). The “price” of this is that we get `T_1` and `T_2` (transforms to the arbitrary frame C) rather than directly the transform between sensor frames. However, as shown next, we can recover the relative extrinsic easily from `T_1` and `T_2` ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=Let%20be%20the%20true%20transformation,can%20be%20recovered%20as%20follows)).

## 3. Computing the Extrinsic Calibration (Relative Transform)

After GMM alignment, the code computes the final extrinsic calibration result. This involves extracting each sensor’s pose in the calibration frame and then finding the transform between sensor frames:

- **Extract final transforms for each sensor:** The list **`AllT[-1]`** contains the final rotation and translation for every point cloud. It is a tuple: `AllT[-1][0]` is the list of final rotation matrices `R_i` for all i, and `AllT[-1][1]` is the list of final translation vectors `t_i` for all i. Using this, the code constructs homogeneous transformation matrices for each point cloud: 

  ```python
  T_1 = [transformPCDs.homogeneous_transform(AllT[-1][0][i], AllT[-1][1][i].reshape(-1))
         for i in range(nObs // 2)]
  T_2 = [transformPCDs.homogeneous_transform(AllT[-1][0][i], AllT[-1][1][i].reshape(-1))
         for i in range(nObs // 2, nObs)]
  ``` 

  Here `nObs//2` is N (the number of frames per sensor). **`T_1`** becomes a list of 4×4 homogeneous matrices for sensor 1’s frames (i = 0...N-1) and **`T_2`** for sensor 2’s frames (i = N...2N-1) ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=TV%2C%20AllT%2C%20pk%3D%20jgmm,i)). Each 4×4 matrix combines the rotation and translation found by GMM for that particular scan. For example, `T_1[i]` is the transform that maps points from sensor1’s **original frame** (after initial alignment) to the calibration frame C (the frame of the model X). Likewise, `T_2[i]` maps sensor2’s frame to the calibration frame. In other words:
  - If **S1_i** is the coordinate frame of sensor1 for frame i, and **C** is the calibration (target) frame, then `T_1[i]` corresponds to \(T_{S1_i \to C}\) (the homogeneous transform from S1 to C).
  - If **S2_i** is sensor2’s frame for the i-th capture, then `T_2[i]` is \(T_{S2_i \to C}\).

  These matrices `T_1[i]` and `T_2[i]` incorporate any initial transform and the additional adjustment from the EM optimization. If the initial guess was perfect and the data noise-free, each `T_1[i]` and `T_2[i]` might be very similar across frames and reflect the true sensor poses in frame C.

- **Compute per-frame sensor-to-sensor extrinsics:** Given each pair of frames (sensor1 vs sensor2) observing the same scene, we can derive the relative transform between the two sensor coordinate systems. The code calculates a list **`T_calib`** as:

  ```python
  T_calib = [np.dot(np.linalg.inv(T_2[i]), T_1[i]) for i in range(len(T_1))]
  ``` 

   ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=for%20i%20in%20range,T_final))This formula takes the inverse of sensor2’s transform and composes it with sensor1’s transform. For each frame index i (0 to N-1):
  - \(T_2[i]^{-1} = T_{C \to S2_i}\) (the transform from the calibration frame to sensor2’s frame).
  - Multiplying \(T_2[i]^{-1} * T_1[i]\) gives \(T_{S1_i \to S2_i}\). This is the **relative transformation from sensor1’s coordinate frame to sensor2’s coordinate frame** for that observation ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=Let%20be%20the%20true%20transformation,can%20be%20recovered%20as%20follows)). In other words, if you take a point expressed in sensor1’s frame, multiplying by this \(T_{\text{calib},i}\) will express it in sensor2’s frame coordinates. 

  Equivalently, one could compute the inverse (which would be \(T_{S2_i \to S1_i} = T_1[i]^{-1} * T_2[i]\)), but the choice of order here simply defines which direction the calibration matrix maps. The GMMCalib code chooses \(T_{\text{calib}} = T_{S1 \to S2}\). This means sensor1 is treated as if it’s being transformed into sensor2’s frame. (If instead we want a matrix that maps sensor2 to sensor1, we would take the inverse of the final result.) The crucial point is that this relative transform eliminates the arbitrary calibration frame C: the product \(T_{C \to S2} * T_{S1 \to C}\) yields a direct sensor-to-sensor mapping ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=Let%20be%20the%20true%20transformation,can%20be%20recovered%20as%20follows)). 

  Notably, if the two sensors were perfectly calibrated (no extrinsic error), we would expect \(T_{S1 \to S2}\) to be the same for all frames and equal to the true extrinsic transform. Mis-calibration would manifest as differences in these per-frame transforms (i.e., each frame pair would require a slightly different alignment).

- **Averaging the extrinsic across frames:** In practice, noise and sampling can cause slight variations in \(T_{S1 \to S2}\) estimates for each frame. GMMCalib addresses this by averaging these transforms to produce a robust final answer. The list `T_calib` (length N) is fed into `transformPCDs.mean_transform(T_calib)`, which computes the average rotation (via mean Euler angles) and average translation ([GMMCalib/src/transformPCDs.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/transformPCDs.py#:~:text=def%20mean_transform)) ([GMMCalib/src/transformPCDs.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/transformPCDs.py#:~:text=return%20euler_to_homogeneous%28np.rad2deg%28euler_mean%29)). This returns a single homogeneous matrix **`T_final`** ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=for%20i%20in%20range,T_final%2C%20X%5D%20with)). Essentially:
  - It extracts the Euler angles (roll, pitch, yaw) from each matrix in `T_calib` ([GMMCalib/src/transformPCDs.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/transformPCDs.py#:~:text=euler_list%20%3D%20,in%20T)), converts to degrees, and averages each angle component.
  - It also averages the \(t_x, t_y, t_z\) translation components across all frames ([GMMCalib/src/transformPCDs.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/transformPCDs.py#:~:text=euler_list%20%3D%20,in%20T)).
  - Then it converts the mean Euler angles back to a rotation matrix and combines with the mean translation to form the mean transform ([GMMCalib/src/transformPCDs.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/transformPCDs.py#:~:text=return%20euler_to_homogeneous%28np.rad2deg%28euler_mean%29)).

  The result **`T_final`** is the estimated **extrinsic calibration matrix** between the two LiDARs. In the code, `T_final` is printed out and labeled as "Calibration Error" ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=T_1,as%20f%3A%20pickle.dump%28gmmcalib_result)), and then saved to file. The term “Calibration Error” here reflects that this transform represents the correction needed to align the sensors (if the sensors were initially perfectly aligned, this matrix would be identity – zero error). In other words, `T_final` is effectively the **extrinsic calibration error transform** between sensor frames S1 and S2 ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=Let%20be%20the%20true%20transformation,can%20be%20recovered%20as%20follows)). Once applied, it brings the sensors into proper alignment.

- **Interpretation of `T_final`:** Since the code computed \(T_{S1 \to S2}\), the `T_final` matrix can be interpreted as follows: it has a 3×3 rotation (R) and 3×1 translation (t) such that \( \mathbf{p}_{S2} = R \mathbf{p}_{S1} + t \). This maps coordinates from sensor1’s frame to sensor2’s frame. If one prefers the transform from sensor2 to sensor1, one can take \(T_{final}^{-1}\). In either case, this matrix fully describes the extrinsic relationship (rotation and translation offset) between the two LiDAR sensors.

Finally, the script saves the results in `output/gmmcalib_result.pkl` which contains `[T_final, X]` ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=transformPCDs.mean_transform%28T_calib%29%20print%28,Run)) – i.e., the calibration matrix and the reconstructed target point cloud. This allows offline analysis or validation (for example, comparing `X` to a CAD model of the target, or comparing `T_final` to a ground-truth extrinsic if known).

## 4. Frames and Transforms: Global vs Relative

It’s important to distinguish between transforms in the **global (calibration) frame** and the **relative transforms between sensor frames**:
- **Global/Calibration Frame Transforms (T₁, T₂):** In GMMCalib, the calibration frame C is the coordinate system in which the point clouds are aligned during the GMM registration. In our code, after initial processing, the global frame is essentially the vehicle/world frame (since we applied `compute_global_transform` to each cloud) ([GMMCalib/src/generatePCDs.py at main · TUMFTM/GMMCalib · GitHub](https://github.com/TUMFTM/GMMCalib/blob/main/src/generatePCDs.py#:~:text=if%20sensor%20%3D%3D%20sensors)). The GMM algorithm, however, might effectively redefine the frame slightly (since it optimizes both sensors’ poses). The matrices in `T_1` and `T_2` are transformations from each sensor’s local frame to this calibration frame C. For example, `T_1[i] = T_{S1 \to C}` and `T_2[i] = T_{S2 \to C}` ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=,the%20source%20frame%20and%20as)). These include the initial guess plus any adjustments found by the EM optimization. They can be thought of as the estimated poses of sensor1 and sensor2 (for each frame) in the common coordinate system.
- **Relative Sensor-to-Sensor Transform (T_calib / T_final):** The goal of extrinsic calibration is exactly to find the spatial transform between the sensor frames ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=object%20detection%2C%20but%20errors%20propagate,spatial%20transformation%20between%20sensor%20frames)). `T_calib[i] = T_{S1 \to S2}` for each frame i is a relative transform computed by eliminating the calibration frame: \(T_{S1 \to S2} = T_{C \to S2} \circ T_{S1 \to C}\) (using the inverse of one) ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=Let%20be%20the%20true%20transformation,can%20be%20recovered%20as%20follows)). This relative transform does **not depend on the global frame** choice – it’s purely the direct relationship between the two sensor coordinate systems. The final averaged `T_final` is our best estimate of this transform. It is in essence the corrected extrinsic **calibration matrix** that one would use in sensor fusion or mapping to transform data from one LiDAR to the other’s frame.

By introducing the calibration frame (latent target frame) C, GMMCalib avoids biasing the solution towards either sensor ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=registration%20methods%20such%20as%20Iterative,We%20perform%20simulation%20experiments%20using)). Both sensors’ data contribute equally to defining C (often centered around the target). The extrinsic calibration error is manifested as the difference between T₁ and T₂, which GMMCalib computes. In equation form: if the true extrinsic (calibration) between sensor 1 and 2 is \(T_{\text{true}}\), and sensors were initially misaligned, then \(T_{\text{true}}\) represents the error transform between their frames ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=coordinate%20frames%20and%20representing%20the,calibration%20frame)). Given estimates T₁ and T₂ to a common frame, GMMCalib recovers \(T_{\text{calib}} \approx T_{\text{true}}\) by \(T_{S1 \to S2} = T_2^{-1} T_1 ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=Let%20be%20the%20true%20transformation,can%20be%20recovered%20as%20follows))\). 

To summarize the **major variables in `gmmcalib.py` and their roles**:
- **`pcds`:** list of input point cloud objects for each sensor frame (after initial alignment and cropping).
- **`V`:** list of point coordinate arrays extracted from each pcd (size nObs = M point sets).
- **`Xin`:** initial model (target) points array for GMM (e.g. a cube’s points in approximate target location).
- **`X`:** output model points array (reconstructed target in calibration frame).
- **`TV`:** list of transformed point arrays (each input cloud aligned to the model).
- **`AllT` (or `T` in code comments):** list of (R, t) transformations for all scans at each EM iteration. `AllT[-1]` is the final tuple of rotations and translations.
- **`T_1`:** list of homogeneous transform matrices for sensor 1 frames to calibration frame (constructed from final R,t for frames 1..N).
- **`T_2`:** list of homogeneous transform matrices for sensor 2 frames to calibration frame (frames N+1..2N).
- **`T_calib`:** list of relative transforms between sensor frames for each pair (computed as \(T_{S1\to S2}\) per frame by combining T₁ and T₂) ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=for%20i%20in%20range,T_final)).
- **`T_final`:** the averaged calibration transform (a single 4×4 matrix) representing the extrinsic calibration result (sensor1 → sensor2). This is the correction (error transform) that calibrates the sensors ([github.com](https://github.com/TUMFTM/GMMCalib/raw/refs/heads/main/src/gmmcalib.py#:~:text=for%20i%20in%20range,as%20f%3A%20pickle.dump%28gmmcalib_result)).

**Extrinsic calibration output:** The matrix `T_final` can now be used in practice to project point clouds from one LiDAR into the other’s coordinate frame (or into a vehicle frame, if one sensor’s pose in vehicle frame is known). GMMCalib prints this matrix as the final result, and its magnitude (how far from identity it is) indicates the severity of the initial miscalibration that was corrected. For example, if `T_final` has a rotation of a few degrees and a translation of a few centimeters, that was the initial extrinsic error. After calibration, applying `T_final` (or its inverse, depending on convention) aligns the two LiDAR point clouds accurately in a common frame ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=coordinate%20frames%20and%20representing%20the,calibration%20frame)).

In conclusion, GMMCalib’s pipeline involves (**1**) preparing and roughly aligning the data, (**2**) using a probabilistic EM algorithm to jointly register all point clouds and build a consistent model, and (**3**) extracting the sensor-to-sensor transformation from the result. This approach improves robustness to initialization and noise by leveraging all observations and a proper statistical model ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=registration%20methods%20such%20as%20Iterative,We%20perform%20simulation%20experiments%20using)) ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=However%2C%20among%20local%20registration%20methods%2C,methods%20aim%20to%20avoid%20selecting)). The outcome is both a refined calibration target reconstruction and a reliable extrinsic calibration matrix between the LiDAR sensors. The distinction between the global calibration frame transforms (T₁, T₂) and the relative extrinsic transform (T_calib/T_final) is crucial: the former situates each sensor in a common space, while the latter is the quantity of interest – the direct rigid transform between the sensor frames ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=The%20goal%20of%20extrinsic%20calibration,sensor%20frames%20are%20transformed%20into)) ([[2404.03427] GMMCalib: Extrinsic Calibration of LiDAR Sensors using GMM-based Joint Registration](https://ar5iv.org/abs/2404.03427#:~:text=Let%20be%20the%20true%20transformation,can%20be%20recovered%20as%20follows)). The GMMCalib code elegantly computes this step-by-step as described, yielding the final calibration output for use in sensor fusion and mapping tasks.

Excellent question — and this gets right to the heart of interpreting what `T_final` **actually represents** in GMMCalib.

---

## ✅ Short Answer:

If both `transform_sensor_1` and `transform_sensor_2` are **perfect** (i.e., they represent the **true extrinsic calibration** of each sensor to the global/world frame), and you apply them **before registration** (to transform all point clouds into the same global frame), then:

### ✅ `T_final` **should be the identity matrix**  
\[
T_{\text{final}} \approx I_{4x4}
\]

Or at least **very close to identity**, within numerical tolerance.

---

## 🧠 Why?

### Because in that setup:

1. You use `transform_sensor_1` and `transform_sensor_2` to put all your point clouds in the **world/global frame**.
2. Since those transforms are perfect, the clouds are already **aligned** relative to each other — they don’t need correction.
3. When GMMCalib runs:
   - It estimates new transforms `T_1[i]` and `T_2[i]` from each sensor to the latent model frame (C).
   - If the model frame ends up aligning with the global frame (or nearly so), then the difference:
     \[
     T_{\text{calib}}[i] = T_2[i]^{-1} \cdot T_1[i]
     \]
     will be close to the true relative transform between the sensors.
4. And since **your initial transforms were already perfect**, `T_1[i]` and `T_2[i]` are already correct — so their relative difference:
   \[
   T_{\text{final}} = \text{mean}(T_2^{-1} \cdot T_1)
   \]
   will be the **identity matrix** (i.e., no correction needed).

---

## 🧪 Important Clarification

> 🛑 `T_final = I` **does not mean** the two sensors occupy the same position or share a frame.  
> ✅ It means: “After transforming the point clouds using the **true known extrinsics**, the sensors are already aligned — no calibration error remains.”

---

## 🧭 TL;DR

> ✔ If `transform_sensor_1` and `transform_sensor_2` are **perfect**, and you use them to bring all clouds into a common global frame **before** running GMMCalib:
>
> 🔹 Then the estimated `T_final` (i.e., extrinsic calibration error) will be:
> \[
> T_{\text{final}} \approx \mathbf{I}_{4x4}
> \]
> Meaning: No further correction is needed. Calibration succeeded.
